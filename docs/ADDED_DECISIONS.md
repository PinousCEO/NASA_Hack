# 자율적으로 추가·결정한 내용

지시서 §13에 따라, 기획 충족에 필요하다고 판단해 묻지 않고 넣은 것들을 기록한다.
형식: 추가 내용 / 필요한 이유 / 연결되는 요구사항 / 대안과 선택 이유 / 영향 범위 / 검증 결과.

## D-01 회선이 없으면 부품이 동작하지 않는 "배선 필수" 모델

- **추가 내용**: `config.systems.links`(전력·데이터·제어 회선)와 `systems.wired` 플래그. 배선된 미션에서는 전력선이 없으면 부품이 꺼지고, 데이터선이 없으면 관측 데이터가 기록되지 않으며, 제어선이 없으면 제어 로직이 명령하지 못한다. 선마다 정격(W, bit/s)과 질량이 있다.
- **이유**: "회선은 실제 흐름을 전달해야 한다"(§7)를 장식선이 아닌 계산으로 만들려면, 선의 유무와 정격이 전력·데이터 예산을 바꿔야 한다.
- **연결**: R-BUILD-01, R-BUILD-02, R-FLOW-02, E03, E09.
- **대안**: (a) 선을 그림으로만 표시 — 기획 위반. (b) 임의 토폴로지 전력망 해석 — 하루 안에 검증 불가. → 버스를 중심으로 한 별(star)형 분배 + 정격 제한 모델을 택했다.
- **영향**: 엔진의 모든 예산 계산(`recalc.ts`)이 "배선을 거친 실제 동작 부품"으로 수행된다. 질량 예산에 하네스 질량이 추가됐다. 기존 테스트가 쓰는 미배선 구성은 `wired:false`로 종전과 같이 동작한다.
- **검증**: `tests/systems.test.ts`(배선 5건), `reports/evidence/ui-systems.md`.

## D-02 미션은 "배선이 끝난 상태"로 시작하고, 새 부품은 미연결로 도착

- **추가 내용**: 미션 생성 시 모든 초기 부품에 표준 하네스를 자동 배선(`prewire`). 카탈로그에서 직접 추가한 부품은 미연결로 올라오고, 부품 카드의 **Connect it** 또는 AI가 연결한다. AI에게 "달아줘"라고 하면 연결까지 한다(`connect: true`).
- **이유**: "미션 시작 시 빌드가 완료되어 있어야 한다"(§5)와 "필요한 회선을 AI에게 물어본다"(§6)를 동시에 만족시키기 위해.
- **대안**: 새 부품도 자동 배선 — 회선이 의미 없는 장식이 된다.
- **영향**: 카탈로그 추가 후 연결하지 않으면 목표가 달성되지 않는다(경고 표시와 연결 버튼 제공).
- **검증**: `reports/evidence/ui-systems.md`, `reports/evidence/play-*.md`.

## D-03 정격이 모자란 선은 부품을 제한 — "선 교체"가 설계 선택이 됨

- **추가 내용**: 태양전지판을 키우거나 장비 전력을 올리면 기존 선의 정격을 넘는 만큼 잘린다. `Connect it`은 모자란 선의 정격도 올려 준다(질량 증가).
- **이유**: 실제 흐름·단위 검증(§7). 수치만 올리면 끝나는 슬라이더 게임이 되는 것을 막는다.
- **영향**: 슬라이더로 부품을 키운 뒤 배선 경고가 뜰 수 있다. 경고 문구가 원인과 해결을 말한다.
- **검증**: `tests/systems.test.ts` "carries only what a line is rated for".

## D-04 제어 로직 = 제한된 규칙 언어(자체 파서), eval 없음

- **추가 내용**: `systems.controllers` — "WHEN 조건 → 대상에 값 설정" 규칙 목록, 기억 변수(히스테리시스), 다운링크 우선순위. 조건·값은 자체 토크나이저/파서(`src/systems/expr.ts`)로 트리로 만들어 평가한다. 길이·노드 수·중첩 깊이 제한, 미리 정의된 신호와 함수만 허용.
- **이유**: "새 동작을 실제로 정의·실행"(§7)하면서 "무제한 eval 금지"를 지키려면 실행 모델 자체가 닫혀 있어야 한다.
- **대안**: 기존 QuickJS 샌드박스 스크립트를 매일 호출 — 가능하지만 느리고, 모델이 만든 코드의 타입 검증 실패율이 높았다(기존 `generate_script` 경로). 규칙 언어는 LLM이 구조화 출력으로 안정적으로 만든다.
- **영향**: 제어기는 비행 시뮬레이션에서 하루 1회 실행된다(일 평균 모델). 실시간 비행 소프트웨어가 아님을 UI와 가정에 명시.
- **검증**: `tests/systems.test.ts`(적대적 입력 12종 거부, 비행 결과 변화, 재현성), 실제 모델 실행 `reports/evidence/e05-e06-build-control.md`(전력 부족일 155→0).

## D-05 제어 로직은 제안 단계에서 "실제로 날려 보고" 전후를 보고

- **추가 내용**: 제어기를 추가·변경하는 제안은 같은 임무·같은 비행 중 사건으로 변경 전후를 모두 비행시켜, 회수 데이터·손실·전력 부족일·제어기 작동일·장비별 회수량을 제안 설명과 테스트(`systems.flight`)에 넣는다.
- **이유**: "시험 환경에서 실행, 전후 비교"(§6·§7), "AI가 가능하다고 말한 것과 모델로 검증된 것을 분리".
- **영향**: 제어기 제안 1건당 시뮬레이션 2회(각 0.1초 내외).
- **검증**: `tests/crew-ai.test.ts`, 실제 모델 실행 증거.

## D-06 검증에서 거부된 AI 연산은 사유와 함께 모델에 되돌려 재시도(최대 2회)

- **이유**: "실패하면 원인을 분석하고 수정안을 만들어 재검증"(§6). 잘못된 포트·없는 신호를 쓰는 첫 시도가 사용자에게 실패로 보이지 않게 한다.
- **한계**: 세 번 모두 거부되면 아무것도 만들지 않고 마지막 거부 사유를 그대로 알린다.
- **검증**: `tests/crew-ai.test.ts` "sends operations that validation rejects back to the model".

## D-07 개인 AI 대화는 기본 비공개, 공유는 본인이 선택

- **추가 내용**: 요청 기록에 `shared` 플래그. 다른 플레이어는 HTTP·WebSocket 모두에서 "누가 자기 AI와 대화 중"이라는 표식만 본다. 공유 세계에 적용되는 변경(제안 요약, 승인 버튼)은 모두에게 보인다. 카탈로그 추가·연결 같은 직접 조작은 처음부터 공개.
- **이유**: §10 "개인 대화를 무조건 공개하지 마라".
- **대안**: 전부 공개(기존 동작) — 지시 위반. 완전 분리 — 제안 승인이 불가능해진다.
- **검증**: `tests/crew-ai.test.ts`, `reports/evidence/ui-crew.md`.

## D-08 플레이어별 대화 문맥

- **추가 내용**: 분석 프롬프트에 그 플레이어의 최근 6개 문답만 넣는다. 다른 플레이어의 대화는 들어가지 않는다. 공유 세계는 항상 최신 미션 구성을 넣는다.
- **검증**: `tests/crew-ai.test.ts`(프롬프트 내용 단언), 실제 모델이 "기존 제어기에 추가"로 이어서 작업.

## D-09 "임무가 성립하는가"를 점수보다 먼저

- **추가 내용**: 평가에 `outcome`(not_ready / ready_to_fly / success / partial / failed)과 조건별 근거. 왼쪽 패널 최상단과 디브리프 최상단에 표시. 판정 규칙은 "게임 규칙"으로 명시.
- **이유**: §8 "임무 달성 여부와 근거 지표를 먼저, 점수는 보조".
- **검증**: `reports/evidence/ui-crew.md`, `reports/evidence/play-*.md`.

## D-10 3D 시스템 뷰의 선 = 실제 회선

- **추가 내용**: 꺼 두었던 연출용 흐름선을 제거하고, 설계에 실제로 있는 선만 종류별 색으로 그린다(전력 주황, 데이터 청록, 제어 보라). 미연결 부품에는 선이 없다. 버스의 이유 없는 자전 연출을 제거.
- **이유**: §11 "설명 없는 무한 회전" 금지, 장식과 상태의 구분.
- **검증**: `reports/evidence/xr-loop.md`(선 개수 9→12, Web·MR 동일).

## D-11 헤드셋 상태 패널과 빠른 명령이 설계 상태를 따름

- **추가 내용**: MR 상태 패널 첫 줄이 임무 판정, 이어서 미충족 조건·배선·제어 로직. 빠른 명령은 미연결 부품이 있으면 "Connect …", 제어기가 없으면 "Add power-saving logic", 있으면 "Fly the mission" 등으로 바뀐다. 선택한 부품의 연결 상태를 말한다.
- **이유**: §9 Web과 MR이 같은 작업 흐름을 가져야 한다.
- **검증**: IWER 에뮬레이터 `reports/evidence/xr-loop.md`. 실기기 미검증.

## D-12 공유 시계의 단계 실행 버튼

- **추가 내용**: 시계 덱에 −1 d / −1 h / +1 h / +1 d. 기존 재생·정지·3단 배속과 함께 전원 공유.
- **이유**: §8 "속도, 일시정지, 단계 실행 공유".

## D-13 야간 실행 장치

- **추가 내용**: 프로젝트 범위 Stop 훅(`.claude/settings.json` → `.claude/nightshift-stop.cjs`). 08:00 KST 전에는 턴 종료를 막고 다음 작업을 지시한다. 중지 파일 `NIGHTSHIFT_STOP`, 다른 세션 무시, 10분 내 6회 이상 막으면 통과(실제 차단 요인과 싸우지 않도록).
- **한계**: 세션 프로세스 자체가 죽거나 사용량 한도에 걸리는 경우는 다루지 못한다. 외부 감독 프로세스는 만들지 않았다(이 환경에서 `claude` 실행 파일을 중첩 실행할 수 없었고, 권한 우회 없이 가능한 가장 단순한 구조를 택함).
- **검증**: 파이프 테스트 3종 + 같은 설정 파일의 임시 PostToolUse 프로브가 이 세션에서 실제 발화함을 확인.

## D-14 아이디어 판정 분류와 "Did not hold" 보관함

- **추가 내용**: AI가 아이디어를 조건부(conditional) / 성립 안 함(refuted) / 모델 범위 밖(outside_model)으로 분류해 답변에 표시한다. 거부된 아이디어는 My AI의 **Did not hold** 보기에서 이유와 함께 남고, 본인이 공유하면 다른 승무원이 읽는다.
- **이유**: §6 "가능성 있음, 조건부 가능, 제약 위반, 정보 부족 구분", §8 "실패한 가설도 이유와 함께 남겨 다른 플레이어가 개선".
- **한계**: 분류 자체는 언어 모델의 판단이다(화면에 "모델 판단"으로 표시). 만들어 측정한 결과만 엔진 계산이다.
- **검증**: `tests/crew-ai.test.ts`, `reports/evidence/ui-fullflow.md`.

## D-15 개인 대화에서 나온 연구 기록도 본인만 열람

- **추가 내용**: 대화에서 생긴 연구 기록(요청 문장, 계획, 실패)에 소유자를 표시하고, 연구 기록 목록·검색·단건 조회와 "유사한 과거 작업" 검색에서 본인에게만 보이게 했다.
- **이유**: D-07의 비공개 원칙이 연구 기록 화면으로 새는 것을 야간 점검 중 발견했다.
- **검증**: `tests/crew-ai.test.ts`(다른 계정은 목록에서 못 보고 단건 조회는 404).

## D-16 분석 스크립트 생성의 검증·수정 반복

- **추가 내용**: 모델이 쓴 스크립트를 생성 단계에서 바로 정적 검증하고 샌드박스에서 한 번 실행해, 거부 사유를 모델에 돌려 최대 2회 고치게 한다.
- **이유**: 실제 모델의 스크립트가 타입 검증에서 떨어지는 경우가 있었다(§6 "실패하면 원인을 분석하고 재검증").
- **검증**: `tests/crew-ai.test.ts`, 실제 모델 1건(`reports/evidence/script-generation.md`).

## D-17 언어 모델 키 없이도 문장으로 연결

- **추가 내용**: 규칙 기반 분석기가 "connect the neutron spectrometer", "wire up inst1"을 이해한다.
- **이유**: §14 "키가 없어도 인증 없이 가능한 작업은 계속".
- **검증**: `tests/systems.test.ts`.

## D-18 3D에서 미연결·정격 부족 부품 표시

- **추가 내용**: 시스템 뷰의 부품 라벨이 연결 상태를 먼저 말한다 — 빨강 "NOT CONNECTED · no power line", 주황 "LINE TOO SMALL · n% gets through".
- **이유**: §11 "현재 무엇이 부족하거나 잘못됐는가"를 글을 읽지 않고도 보이게.

## D-19 제어 로직과 배선이 실제 해법이 되는 초기 문제: "축소된 태양전지판"

- **추가 내용**: 미션 변형 `lean-array`(태양전지판이 계획의 절반)와 내장 브리프 "Short on power in the long shadow". 장비를 달면 연중 일부 기간 전력이 모자란다. 더 큰 전지판(+더 굵은 전력선·질량·비용), 궤도면 변경, 관측 가동률 조정, 전력이 모자랄 때만 부하를 줄이는 제어 로직이 모두 해법이고 대가가 다르다.
- **이유**: 기본 미션은 전력 여유가 커서 AI가 만든 제어 로직이 "작동한 날 0일"로 끝나는 경우가 많았다. §5 "초기 설계에서 해결해야 할 부족한 역량"과 §7의 제어 로직이 플레이에서 의미를 갖게 하려면 그것이 필요한 문제가 있어야 한다.
- **영향**: 기존 시드의 미션은 바뀌지 않는다(무작위 추첨 목록에는 넣지 않고, 브리프가 지정할 때만 적용). AI가 쓰는 브리프도 이 변형을 고를 수 있다.
- **검증**: `tests/lean-array.test.ts` — 3개 시드에서 문제가 실제로 발생, 하드웨어 해법과 제어 로직 해법 모두 전력 부족일을 줄이고, 질량과 수집 데이터에서 서로 다른 대가를 치름.

## D-20 AI가 현재 설계의 전체 비행 결과를 읽음

- **추가 내용**: AI의 미션 문맥에 "flight"를 넣었다 — 현재 설계를 그 미션의 비행 중 사건으로 즉시 비행시킨 결과(합계, 전력이 모자란 기간과 날짜, 연중 표본값, 사건, 장비별 데이터, 제어 로그).
- **이유**: "연중 언제 전력이 모자라?" 같은 질문에 AI가 답하지 못했다(97초 뒤 불가 응답). §6 "오래된 대화만 보고 현재 세계를 추측하지 마라".
- **영향**: 요청마다 시뮬레이션 1회(약 0.1초) 추가. 표본 간격(1–4일)을 문맥에 명시.
- **검증**: 실제 모델이 같은 질문에 날짜로 답함(`reports/evidence/lean-array-play.md`).

## D-21 각 AI가 자기 플레이어의 좌석을 앎

- **추가 내용**: 요청마다 그 플레이어의 이름, 맡은 좌석과 임무, 다른 좌석과 담당자를 AI에게 준다. 아이디어가 다른 좌석의 영역(전력·질량·데이터·비용)에 영향을 주면 누구와 이야기해야 하는지 말하게 했다.
- **이유**: 사용자 기획 — "4명의 플레이어가 각각 자신의 AI와 대화하면서 자신들이 맡은 미션을 수행".
- **검증**: `tests/crew-ai.test.ts`(좌석을 맡은 사람과 아닌 사람의 프롬프트가 다름).

## D-22 비행 결과의 근거 표시와 "이길 수 있음"의 고정

- **추가 내용**: Analysis 탭의 비행 결과에 장비별 회수/손실 데이터와 제어 로직 로그(일자별). 플레이 가능성 테스트에 "풀이가 끝난 설계는 not ready/failed가 아니고, 모든 미션에 완전 성공이 존재" 단언 추가.
- **검증**: `reports/evidence/ui-flight.md`, `tests/playability.test.ts`.

## 하지 않기로 한 것

- **정답 제시형 조언기**: 사용자 지시("플레이어가 다양한 방법으로 풀어야 한다")에 따라 제품에 넣지 않는다. 풀이기는 테스트 지원 코드에만 있다.
- **한국어 UI**: 제품 UI는 영어 유지(사용자 지시). 플레이어는 한국어로 AI에게 말할 수 있고 AI는 같은 언어로 답한다.
- **외부 유료 3D 생성 서비스·추가 과금**: 사용하지 않았다. 3D 외형은 내장 파라메트릭/절차 생성기.
